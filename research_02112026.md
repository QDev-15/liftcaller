### 1.3 Data model thực tế (SQL Server, DB `PLC`)

**`dbo.LiftState`** — đúng 1 dòng (`CHECK (Id=1)`)
- `Id` (PK, =1), `IsRunning` (bit), `UpdatedAt`, `UpdatedBy` (nvarchar — tên terminal cập nhật)

**`dbo.LiftCall`** — tối đa 1 dòng/số máy (PK = `UnitNo`)
- `UnitNo` (PK), `CallType` (tinyint, CHECK IN 1,2,3: 1=Product Pickup, 2=Return Material, 3=Trouble), `Palette` (tinyint, CHECK 0-3: 0=None,1=A,2=B,3=C), `CalledAt` (default SYSDATETIME), `IsResponding` (bit), `RespondedAt`
- Index: `IX_LiftCall_CalledAt (CalledAt, UnitNo)` → **xác nhận thứ tự hàng đợi là FIFO theo thời gian gọi, không có ưu tiên Trouble** (xem §5)

**`dbo.LiftCallHistory`** — lịch sử sau khi Complete
- `HistoryId` (PK, IDENTITY), `UnitNo`, `CallType`, `Palette`, `CalledAt`, `RespondedAt` (null nếu complete thẳng không qua respond), `CompletedAt`, `CompletedBy`
- 2 cột **computed/PERSISTED**: `DurationSeconds = DATEDIFF(SECOND, CalledAt, CompletedAt)`, `ResponseWaitSeconds = DATEDIFF(SECOND, CalledAt, RespondedAt)`
- Index: `IX_LiftCallHistory_CompletedAt`, `IX_LiftCallHistory_UnitNo (UnitNo, CompletedAt)`

**Ghi chú quan trọng về DB:**
- **Không có Foreign Key** nào giữa 3 bảng — tất cả liên kết qua `UnitNo` chỉ bằng convention, không ràng buộc DB.
- `LiftCall` và `LiftCallHistory` **loại trừ lẫn nhau theo thời gian**: khi Complete, API chạy 1 transaction `BEGIN TRAN → INSERT INTO LiftCallHistory → DELETE FROM LiftCall → COMMIT` (trong `SqlServerLiftCallRepository.CompleteCallAsync`).
- **Cancel không ghi lịch sử** — chỉ `DELETE FROM LiftCall`, không có dòng nào trong `LiftCallHistory`. Nghĩa là **không thể biết được** từ DB có bao nhiêu cuộc gọi đã bị hủy, chỉ biết cuộc gọi nào đã hoàn thành.
- **Gọi lại (re-call) sẽ ghi đè** dòng cũ qua `MERGE ... WHEN MATCHED THEN UPDATE SET CalledAt = SYSDATETIME(), IsResponding = 0` — đây là một **bug tiềm ẩn** (xem §4.3).

## 2. Cách chạy code trên máy mới

1. **Yêu cầu**: .NET 8 SDK, Visual Studio 2022 (hoặc `dotnet` CLI), SQL Server (hoặc dùng `"Storage": "Memory"` để test không cần DB).
2. **Clone/copy** toàn bộ thư mục `alumiLiftCall`.
3. **Cấu hình `LiftCall.Api/appsettings.json`**:
   - `"Storage"`: `"Memory"` (test nhanh, không cần DB) hoặc `"SqlServer"` (cần connection string đúng).
   - Nếu dùng SQL Server: chạy `Sql/01_CreateTables.sql` rồi `Sql/02_AddHistory.sql` trên DB đích trước.
4. **Chạy API** (`dotnet run --project LiftCall.Api`, mặc định lắng nghe port theo `launchSettings.json`, ví dụ `http://localhost:5080`).
5. **Chạy Caller**: `LiftCall.Caller.exe <số máy 1-5>` — số máy truyền qua launch argument. Trong Visual Studio dùng multi-startup project hoặc set Command line arguments trong Debug properties.
6. **Chạy Receiver**: `LiftCall.Receiver.exe` — không cần argument (chỉ có 1 terminal hiện tại).
7. **Cấu hình `ApiBaseUrl`** trong `appsettings.json` của Caller/Receiver (qua `LiftCall.Shared/ClientSettings.cs`) để trỏ đúng tới địa chỉ API (localhost khi test trên 1 máy, hoặc IP LAN thật khi test đa máy).
8. **Triển khai lên IIS (production)**: publish `LiftCall.Api` dạng self-contained hoặc framework-dependent, cài **ASP.NET Core Hosting Bundle**, tạo site trong IIS trỏ vào thư mục publish, App Pool chế độ **"No Managed Code"**.

## 3. Hướng dẫn cài IIS qua Windows GUI

1. Mở **Control Panel → Programs → Turn Windows features on or off** (hoặc chạy `optionalfeatures` qua Run/Win+R).
2. Tick **Internet Information Services** → mở rộng cây, đảm bảo tick:
   - **Web Management Tools → IIS Management Console**
   - **World Wide Web Services → Application Development Features → .NET Extensibility, ASP.NET** (nếu cần)
   - **World Wide Web Services → Common HTTP Features** (mặc định đủ dùng)
3. Nhấn OK, chờ Windows cài đặt, khởi động lại nếu được yêu cầu.
4. **Cài ASP.NET Core Hosting Bundle** (tải từ trang .NET download) — bắt buộc để IIS host được ứng dụng ASP.NET Core (`LiftCall.Api`), nếu không cài sẽ lỗi 500.19 hoặc 502.5.
5. Mở **IIS Manager** (`inetmgr`):
   - Tạo **Application Pool** mới: .NET CLR Version = **No Managed Code**, Start Mode = **AlwaysRunning**, Idle Time-out = **0** (tránh App Pool bị recycle khi rảnh, làm mất kết nối polling/WebSocket).
   - Tạo **Site** mới, trỏ Physical Path vào thư mục publish của `LiftCall.Api`, gán Application Pool vừa tạo, đặt Binding (IP + Port, ví dụ port 5080 hoặc 80).
6. Mở **Windows Firewall** (`firewall.cpl` → Advanced Settings → Inbound Rules) để tạo rule cho phép traffic vào đúng port vừa cấu hình (nếu Caller/Receiver chạy trên tablet khác qua LAN).

## 4. Chẩn đoán lỗi runtime

### 4.1 Lỗi gốc được report (qua screenshot)

Khi bấm "Lấy thành phẩm" / "Thu hồi vật liệu" trên app Caller, hiện MessageBox:
> "リフト呼び出し（1号機）— サーバーと通信できませんでした。The request was canceled due to the configured HttpClient.Timeout of 5 seconds elapsing."

**Nguyên nhân gốc (xác nhận bằng công cụ thực tế, không phải giả định):**
- `LiftCall.Api/appsettings.json` có `"Storage": "SqlServer"`, connection string trỏ tới `Server=tochusv51v6` — host này **không resolve/không reachable** (`Test-NetConnection` trả về `TcpTestSucceeded: False`, `RemoteAddress` trống).
- API bị **block** trong `SqlConnection.OpenAsync()` **lâu hơn 5 giây** (thử `curl http://localhost:5080/api/status` treo >10s, exit code 28 = timeout).
- `LiftCallApiClient` (`LiftCall.Shared/LiftCallApiClient.cs` dòng 16) hardcode `HttpClient.Timeout = TimeSpan.FromSeconds(5)` → client timeout **trước khi** API kịp timeout kết nối SQL → lỗi hiển thị ở Caller.
- Polling (`GetStatusAsync`) cũng lỗi tương tự nhưng **âm thầm** (chỉ đổi title, không có MessageBox) — chỉ hành động chủ động (gọi/hủy/complete) mới hiện popup chặn.

**Hướng xử lý (đã đề xuất, chưa áp dụng):**
- Đổi `"Storage": "Memory"` để test không cần DB, **hoặc**
- Sửa đúng connection string (xem §4.2) và restart `LiftCall.Api`.

### 4.2 Lỗi kết nối SQL thứ hai — do typo tên máy

Người dùng cung cấp connection string thực tế để kiểm tra (đã redact mật khẩu khi lưu vào file này vì đây là thông tin nhạy cảm — xem cảnh báo ở §7):
```
Server=QuyhNH;Database=PLC;User Id=sa;Password=********;Encrypt=true;TrustServerCertificate=true;
```

**Nguyên nhân: lỗi chính tả, không phải lỗi cấu hình/bảo mật.**
- Hostname máy thật là **`QUYNHNH`** (xác nhận qua `hostname` và `$env:COMPUTERNAME`), người dùng gõ thiếu chữ "n" → **`QuyhNH`**.
- Xác minh: `Test-NetConnection QuyhNH -Port 1433` → fail. `Test-NetConnection QUYNHNH -Port 1433` và `localhost:1433` → **thành công**.
- Service `MSSQLSERVER` đang **Running**. SQL Server 2022 RTM 16.0.1000.6 Enterprise Edition.
- Login `sa` + mật khẩu đã cho **xác minh hoạt động được** qua `sqlcmd` (`C:\Program Files\Microsoft SQL Server\Client SDK\ODBC\170\Tools\Binn\SQLCMD.EXE`).
- Database `PLC` và cả 3 bảng (`LiftState`, `LiftCall`, `LiftCallHistory`) **đã tồn tại sẵn** trên instance local.

**Hướng xử lý (đã đề xuất, chưa áp dụng):** đổi `Server=QuyhNH` → `Server=localhost` (hoặc `.`) trong `appsettings.json`, restart `LiftCall.Api`.

### 4.3 Bug tiềm ẩn phát hiện qua review code (chưa fix)

- **Re-call ghi đè cuộc gọi đang Responding**: `UpsertCallAsync` dùng `MERGE ... WHEN MATCHED THEN UPDATE SET CalledAt = SYSDATETIME(), IsResponding = 0` — nếu máy đang được phản hồi (`IsResponding = true`) mà công nhân bấm gọi lại (vô tình hoặc do UI chưa rõ), cuộc gọi sẽ bị **reset về trạng thái chưa phản hồi** mà operator phía lift không được thông báo gì, có thể gây hiểu nhầm là "đã xử lý xong nhưng vẫn hiện gọi mới".
- **Receiver tự ép Lift về "Stopped" khi khởi động** (xem §1.7) — rủi ro vận hành nếu Receiver crash/restart trong khi lift đang chạy thật.
- **Timeout 5 giây cứng** trong `LiftCallApiClient` không đủ dự phòng khi mạng Wi-Fi nhà máy chập chờn (đúng rủi ro đã nêu trong tài liệu đề xuất §5.11) — nên tăng lên hoặc thêm retry.

## 5. "Trouble ưu tiên hàng đợi" là gì?

Trong tài liệu kiến trúc đề xuất (CLAUDE.md §5.6, bảng "Mặc định đề xuất"), có câu hỏi mở: **"Trouble có nhảy cóc hàng đợi không?"**, với mặc định đề xuất là **Có** — nghĩa là khi có cuộc gọi loại Trouble (sự cố), nó sẽ **hiện lên đầu danh sách** ở màn hình phía lift, vượt qua các cuộc gọi Product Pickup/Return Material đã gọi trước đó, để operator thấy và xử lý sự cố trước (có thể tắt được qua setting).

**Thực tế trong code hiện tại: chưa có logic này.**
- `GetCallsAsync` trong `SqlServerLiftCallRepository` dùng `ORDER BY CalledAt, UnitNo` — **thuần FIFO theo thời gian gọi**, không phân biệt loại cuộc gọi.
- Tức là nếu máy 1 gọi Product Pickup lúc 10:00, máy 2 gọi Trouble lúc 10:01, thì trên màn hình Receiver, Product Pickup của máy 1 vẫn đứng trước Trouble của máy 2 — **không có ưu tiên**.

Đây là 1 trong các quyết định nghiệp vụ còn mở, cần khách hàng xác nhận trước khi implement (nếu cần thì sửa `ORDER BY` thêm `CASE WHEN CallType = 3 THEN 0 ELSE 1 END, CalledAt`).

## 6. Cơ chế update trạng thái phía Caller hiện tại

Toàn bộ là **HTTP polling**, không có SignalR/WebSocket/push nào:

1. `App.xaml.cs` đọc `ClientSettings.Load()` từ `appsettings.json` (có `ApiBaseUrl`, `UnitNo` mặc định, `PollingSeconds` mặc định = 2), override `UnitNo` nếu có launch argument.
2. `CallerWindow.xaml.cs` khởi tạo một `DispatcherTimer` chạy mỗi `PollingSeconds` giây, gọi `PollAsync()`.
3. `PollAsync()` gọi `GET /api/status`, nhận về toàn bộ `StatusDto` (gồm `LiftStateDto` + danh sách `CallDto` của mọi máy). Nếu lỗi (mất mạng, server down), **chỉ đổi title cửa sổ** báo lỗi — không hiện popup (khác với lỗi khi bấm nút).
4. `ApplyStatus()` tự tìm trong `status.Calls` xem có dòng nào khớp `UnitNo` của chính máy mình không, từ đó tự suy ra trạng thái hiển thị: **Idle → Calling (vàng) → Responding (xanh)**. Không có API riêng "lấy trạng thái của tôi" — client tự lọc từ snapshot chung.
5. Khi người dùng bấm nút (gọi / hủy), app gọi API tương ứng (`PutCallAsync`/`CancelCallAsync`) rồi **gọi `PollAsync()` ngay lập tức** (không chờ tick timer tiếp theo) để UI phản hồi nhanh thay vì phải đợi tối đa `PollingSeconds` giây.
6. Mỗi lần trạng thái đổi (`_lastState` khác giá trị mới), app gọi `LedController` để bật/tắt đèn báo vật lý tương ứng (nếu `Enabled = true`).
7. Có thêm logic Palette (A/B/C) riêng cho nút Product Pickup: `Palette_Click` lưu lựa chọn, `UpdatePaletteUi` cập nhật UI, và `ProductButton.IsEnabled` chỉ bật khi đã chọn 1 pallet.

**Tóm lại**: đây chính là lý do tài liệu đề xuất khuyến nghị SignalR thay cho polling — với polling 2s, độ trễ cập nhật trạng thái giữa các terminal có thể lên tới ~2 giây, và khi mất kết nối ngắn hạn, lỗi bị "nuốt" âm thầm trừ khi người dùng đang bấm nút ngay lúc đó.

## 7. Web hay WPF — tài liệu thiết kế đã chốt gì?

- **Tài liệu kiến trúc mới nhất** (`CLAUDE.md` §5, "Draft for review", ngày 2026-10-28) **khuyến nghị Web app** (Blazor WebAssembly chạy trong Microsoft Edge kiosk mode), với lý do: không cần cài/update client trên tablet, ít thành phần di chuyển hơn, không bị khóa vào tablet Windows.
- Nhưng đây **vẫn chỉ là đề xuất/khuyến nghị**, chưa có xác nhận bằng văn bản từ khách hàng trong các tài liệu đã đọc rằng họ đồng ý đổi từ WPF sang Web.
- **Code thực tế đã viết (`alumiLiftCall`) dùng WPF** — giống yêu cầu gốc của khách hàng (Prompt.txt), không phải theo khuyến nghị Web app mới nhất.
- → Điều này cho thấy: **khách hàng (hoặc đội dev) đã quyết định đi theo WPF** (yêu cầu gốc), hoặc ít nhất đã bắt đầu triển khai theo hướng đó trước khi/independent với tài liệu khuyến nghị Web được hoàn thiện. Tài liệu `CLAUDE.md` nên được cập nhật để phản ánh thực tế này (việc này **chưa được thực hiện** — xem Pending Tasks).
- **Hệ quả về effort**: nếu khách hàng chính thức giữ WPF, theo bảng variant trong tài liệu gốc (§5.10), đây tương ứng với "+8–14 ngày-dev, +2–4 ngày-tester" so với phương án Web — nhưng vì code đã viết theo WPF rồi, phần "variant cost" này coi như đã nằm trong effort đã bỏ ra, không phải chi phí tăng thêm từ đây.

**Khách hàng hiện tại cần (dựa trên yêu cầu gốc + trạng thái code):**

**Mục tiêu & việc tiếp theo (ưu tiên gợi ý):**

## 9. Ví dụ thực tế — một ngày sử dụng hệ thống

**Ngữ cảnh**: 5 máy sản xuất (máy 1-5), 1 tablet Receiver gắn trên xe lift, operator vận hành lift di chuyển liên tục trong xưởng.

1. **08:15** — Công nhân máy 3 đóng gói xong 1 lô sản phẩm, chạm nút **"Lấy thành phẩm"** trên tablet Caller máy 3 (trước đó phải chọn Pallet A/B/C vì nút Product Pickup chỉ bật khi đã chọn pallet). App gửi `PUT /api/calls/3`, server lưu `CallType=1, Palette=1 (A), CalledAt=08:15:00`. Tablet máy 3 chuyển ô trạng thái sang "Calling" (vàng).
2. **08:15:02** (tick polling tiếp theo của Receiver) — Tablet trên xe lift nhận `GET /api/status`, thấy cuộc gọi mới của máy 3, hiển thị thẻ viền xanh "Máy 3 — Lấy thành phẩm — Pallet A" ở cuối hàng đợi, kèm icon LED bật (nếu `LedController.Enabled = true`).
3. **08:16:30** — Cùng lúc, máy 2 báo sự cố, chạm nút **"Trouble"**. Server lưu `CallType=3, CalledAt=08:16:30`. Vì **hiện tại chưa có logic ưu tiên Trouble** (xem §5), thẻ của máy 2 xếp **sau** thẻ của máy 3 trong hàng đợi (vì gọi sau), mặc dù về nghiệp vụ sự cố thường cần ưu tiên — đây là điểm khách hàng cần xác nhận có chấp nhận được không.
4. **08:17:00** — Operator lift đang di chuyển, thấy thẻ máy 3 trên tablet Receiver, bấm **Respond**. Server set `IsResponding=1, RespondedAt=08:17:00`. Lần poll tiếp theo của Caller máy 3 (trong vòng ≤2s) đổi ô trạng thái sang "Responding" (xanh).
5. **08:17:45** — Trong lúc operator đang lấy hàng ở máy 3, công nhân máy 3 **vô tình chạm lại nút "Lấy thành phẩm"** (ví dụ tưởng chưa gửi được do không để ý đèn trạng thái). Vì bug `MERGE` ghi đè (§4.3), dòng `LiftCall` của máy 3 bị **reset `IsResponding = 0, CalledAt = 08:17:45`** — operator đang ở ngay cạnh xe không bị ảnh hưởng ngay, nhưng nếu dữ liệu này được dùng để tính thời gian phản hồi sau này, số liệu sẽ sai (tính lại từ 08:17:45 thay vì 08:15:00 gốc).
6. **08:18:30** — Operator lấy hàng xong, bấm **Complete**. Server chạy transaction: `INSERT INTO LiftCallHistory` (ghi `CalledAt=08:17:45` do bug ở bước 5) rồi `DELETE FROM LiftCall WHERE UnitNo=3`. Thẻ máy 3 biến mất khỏi hàng đợi Receiver, tablet máy 3 trở về "Idle".
7. **08:19:00** — Operator di chuyển tới máy 2, bấm Respond rồi Complete cho cuộc gọi Trouble.
8. **Giữa ca, Wi-Fi xưởng chập chờn 6 giây** (dài hơn 5s timeout) — mọi tablet (Caller + Receiver) đang poll đều gặp lỗi: Caller chỉ đổi title (im lặng), nhưng nếu công nhân bấm nút gọi đúng lúc đó, sẽ hiện **MessageBox lỗi tiếng Nhật** giống trong báo lỗi gốc của người dùng ("サーバーと通信できませんでした...") — đây chính là kịch bản lỗi đã chẩn đoán ở §4.1, xảy ra bất cứ khi nào kết nối mạng/API gián đoạn hơn 5 giây, không chỉ khi SQL Server sai cấu hình.
9. **Cuối ca** — muốn biết hôm nay có bao nhiêu cuộc gọi, xử lý mất bao lâu trung bình: hiện tại **chưa có màn hình admin/export CSV**, chỉ có thể query trực tiếp SQL bằng câu lệnh mẫu có sẵn trong `02_AddHistory.sql` (tính `AVG(DurationSeconds)`, `AVG(ResponseWaitSeconds)` theo `UnitNo, CallType`).

## 11. Việc còn tồn đọng (đã đề xuất, chưa thực hiện — chờ quyết định người dùng)

1. Sửa `LiftCall.Api/appsettings.json`: đổi `Storage` → `Memory`, hoặc sửa connection string (`Server=QuyhNH` → `Server=localhost`), rồi restart API.
2. Cập nhật `CLAUDE.md` để phản ánh đúng: code thực tế dùng **WPF + polling**, không phải Blazor/SignalR như đề xuất.
3. Implement logic **ưu tiên Trouble** trong hàng đợi (sửa `ORDER BY` + setting bật/tắt).
4. Fix bug **re-call ghi đè trạng thái Responding** trong `UpsertCallAsync`/`MERGE`.
5. (Gợi ý thêm, chưa yêu cầu) Xem lại hành vi Receiver tự ép Lift về "Stopped" khi khởi động — xác nhận đây là hành vi mong muốn hay cần sửa.

## Lưu ý bảo mật

- Trong quá trình trao đổi, người dùng đã dán 1 connection string SQL Server thật có chứa **mật khẩu plaintext** của tài khoản `sa`. Mật khẩu đó **đã được redact** (`********`) trong file này và sẽ không được ghi lại dưới dạng plaintext trong bất kỳ tài liệu/artifact nào khác.
- `README.md` của project đã có cảnh báo sẵn: *"パスワードを含むため、Git等に載せないでください。本番は環境変数 ConnectionStrings__LiftCall や IISの環境変数で上書きする方法が安全です。"* (Không đưa mật khẩu vào Git; dùng biến môi trường để override connection string khi lên production). Khuyến nghị tuân thủ đúng cảnh báo này — không commit `appsettings.json` có mật khẩu thật vào git khi project này được init thành git repo trong tương lai.
